# Android 11 framework, native audio, Telecom, and dialer-role audit

Audited `android11/{base,av,Telecomm,PermissionController}`, all at `android-11.0.0_r48` (API 30). Matching framework, native audio, Telecom service code, and PermissionController dialer-role qualification/grants are covered. Vendor HAL implementations, the actual Shizuku helper on API 30, and a physical phone were not tested. Implementation steps are in [ANDROID_COMPATIBILITY_PLAN.md](ANDROID_COMPATIBILITY_PLAN.md).

## Result

This Android 11 baseline supplies the grants required by its native call-audio path: downlink capture checks `RECORD_AUDIO` and `CAPTURE_AUDIO_OUTPUT`, while ordinary telephony TX playback checks `MODIFY_PHONE_STATE`. Shell has all three. Explicit telephony TX selection with PCM and `USAGE_VOICE_COMMUNICATION` automatically requests the incall-music output in an accessible call mode. This path needs neither the dedicated interception helper nor `CALL_AUDIO_INTERCEPTION`.

Recommend API 30 as the provisional stock unrooted implementation minimum, using default-dialer call control on the unmodified baseline. Its companion override command exists, but service classification never returns the companion type, so an override entry does not make an ordinary app's companion service bind. Default-dialer selection must remain an explicit user choice; without it, ordinary unmodified gateway call access is unavailable on this tag. An optional Xposed Telecom hook could instead admit the gateway alongside the existing dialer, as described below; this has not been implemented or tested. Newer verified companion implementations can continue to make dialer replacement optional.

A separate future deployment with effective Xposed audio-permission hooks could justify evaluating an older minimum. If `CAPTURE_AUDIO_OUTPUT` were already handled, satisfying the helper's `RECORD_AUDIO` and record app-op checks would be a small extension; both PCM directions could remain in the helper. API 23 is a conditional feasibility boundary, not a current target. Xposed implementation and older backports are deferred; see the [current workload](ANDROID_COMPATIBILITY_PLAN.md#workload-by-api-level) and [deferred comparison](ANDROID_COMPATIBILITY_PLAN.md#deferred-xposed-scenario).

Source permission/routing feasibility and the planned gateway-only activity's dialer-role qualification are established; successful two-way audio is not. The remaining gates are helper construction, actual grants/app-ops and hidden-API access, role selection and service callbacks on a device, native library loading, and a physical device's input/output profiles and HAL behavior. Preserve the distinction between a buildable APK, a permitted route, and verified remote PCM delivery.

Shell's `CAPTURE_AUDIO_OUTPUT` grant was added in Android 11; the relevant commits are recorded below. Vendor grants may differ, so use actual helper permission/capability checks. A future hooked deployment would need to distinguish declared grants from effective construction/start results; that integration is outside the current port.

## Historical context: preview permission and accessibility workarounds

In 2020, Google briefly introduced `ACCESS_CALL_AUDIO` in an Android 11 developer preview, then removed it soon afterward. The native audio changes are recorded in the `frameworks/av` [addition commit `ac26cf749f457e12a3d8d7456bbcd58a3e028d69`](https://android.googlesource.com/platform/frameworks/av/+/ac26cf749f457e12a3d8d7456bbcd58a3e028d69) and [removal commit `57a3769fb12dc8b2df457e0919850bd976716706`](https://android.googlesource.com/platform/frameworks/av/+/57a3769fb12dc8b2df457e0919850bd976716706). The permission is absent from the audited `android-11.0.0_r48` release. Its preview appearance did not establish a stable call-recording API; the gateway's release-level audio access relies on the shell permissions and native checks documented below.

Since Android 9 (API 28), Android has [restricted microphone access for background apps](https://developer.android.com/about/versions/pie/android-9.0-changes-all#bg-sensor-access). Some call-recorder developers consequently resorted to accessibility services as a workaround for background recording restrictions. These implementations depended on Android version and device behavior.

Android 11's [audio-input sharing policy treats accessibility services specially](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/service/AudioPolicyService.cpp#613), but enabling an accessibility service does not grant `CAPTURE_AUDIO_OUTPUT` or remove the native permission checks for `VOICE_DOWNLINK`. Accessibility-based recording therefore does not establish a supported alternative to the audited privileged gateway audio path.

## Shell permissions and grants

The [shell manifest](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/packages/Shell/AndroidManifest.xml#20) uses `android.uid.shell` and declares:

| Permission | Shell requests it | Relevant grant path |
| --- | --- | --- |
| `RECORD_AUDIO` | Yes, line 183 | Requested dangerous runtime permission; default system-component grants apply to this UID. |
| `CAPTURE_AUDIO_OUTPUT` | Yes, line 315 | Signature/privileged permission; platform-signed privileged shell, with an explicit allowlist entry. |
| `CAPTURE_VOICE_COMMUNICATION_OUTPUT` | No | Separate signature/privileged permission for voice-communication playback capture; output-capture permission does not imply it. |
| `CAPTURE_MEDIA_OUTPUT` | No | Separate signature/privileged permission; relevant to privileged playback-policy registration below. |
| `MODIFY_PHONE_STATE` | Yes, line 136 | Signature/privileged permission; platform-signed privileged shell and allowlist entry. |
| `MODIFY_AUDIO_ROUTING` | No | No corresponding shell grant found in supplied configuration. |
| `MODIFY_AUDIO_SETTINGS` | No | No corresponding shell grant found in supplied configuration. |
| `MANAGE_AUDIO_POLICY` | Yes | Separate permission; not a substitute for routing/settings or capture permissions. |
| `CALL_AUDIO_INTERCEPTION` | No | Not defined in this framework. |
| `MANAGE_ONGOING_CALLS` | No | Not defined in this framework. |

The manifest explains the recording request as needed for a CTS camera recording test, and the output-capture request as needed for `GtsDialerAudioTestCases`. The [shell privileged allowlist block](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/data/etc/privapp-permissions-platform.xml#306) includes `CAPTURE_AUDIO_OUTPUT` at line 435. The [shell build](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/packages/Shell/Android.bp#5) declares `certificate: "platform"` and `privileged: true`; [signature/privileged grant handling](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/services/core/java/com/android/server/pm/permission/PermissionManagerService.java#3551) checks the allowlist and signing relationship.

[`RECORD_AUDIO`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/res/AndroidManifest.xml#1246) is dangerous/instant; [`CAPTURE_AUDIO_OUTPUT`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/res/AndroidManifest.xml#3936) is signature/privileged. The [default grant policy](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/services/core/java/com/android/server/pm/permission/DefaultPermissionGrantPolicy.java#391) grants requested runtime permissions to qualifying system components. [UIDs below the application UID range qualify](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/services/core/java/com/android/server/pm/permission/DefaultPermissionGrantPolicy.java#1598), which includes shell UID 2000. [Runtime grant collection](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/services/core/java/com/android/server/pm/permission/DefaultPermissionGrantPolicy.java#370) passes those permissions as system-fixed grants. Record permission therefore has a grant path, rather than merely a manifest request.

[`platform.xml`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/data/etc/platform.xml#149) assigns audio-setting permissions to media, audioserver, and cameraserver; it does not supply the missing shell routing/settings grants. Runtime diagnostics must check the device's actual grants and record app-op, because supplied AOSP configuration is not a device measurement.

The [documented `VOICE_DOWNLINK` requirement](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/MediaRecorder.java#253) remains `CAPTURE_AUDIO_OUTPUT`; the native checks below now confirm it on this release.

## Native capture and injection recipe

Capture follows `AudioRecord` -> AudioFlinger `createRecord()` -> policy `getInputForAttr()`. [AudioFlinger normalizes the client identity and forwards it](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audioflinger/AudioFlinger.cpp#2000). [Policy checks](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/service/AudioPolicyInterfaceImpl.cpp#458) require recording permission/app-op first, then output-capture permission for `VOICE_DOWNLINK`, before attempting device selection. The telephony RX input classification checks output-capture permission again. The [permission utilities](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/media/utils/ServiceUtilities.cpp#65) check the real client UID's `RECORD_AUDIO` plus record app-op at creation, and start the app-op again when capture starts. [Output capture](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/media/utils/ServiceUtilities.cpp#139) has its own permission check.

The [default engine](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/enginedefault/src/Engine.cpp#578) chooses the voice-call/telephony RX input for `VOICE_DOWNLINK`, `VOICE_CALL`, and `VOICE_UPLINK`. No matching device or input profile can still make opening fail. [Policy classifies telephony RX](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/managerdefault/AudioPolicyManager.cpp#2084) and opens the matching input. [Capture arbitration](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/service/AudioPolicyService.cpp#589) treats the downlink source as virtual and allows its capture; this does not waive the permission checks already performed.

Playback follows `AudioTrack` -> AudioFlinger `createTrack()` -> policy `getOutputForAttr()`. [AudioFlinger replaces untrusted supplied UID/PID with the Binder caller](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audioflinger/AudioFlinger.cpp#761), so supplying a package or client UID cannot acquire privileges. [Telephony TX output classification checks `MODIFY_PHONE_STATE`](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/service/AudioPolicyInterfaceImpl.cpp#267). The ordinary usage/telephony path does not add a `MODIFY_AUDIO_ROUTING` or `MODIFY_AUDIO_SETTINGS` requirement. System usages and policy-mix playback are separate paths with routing checks.

The [engine honors an explicitly preferred output device](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/enginedefault/src/Engine.cpp#659). [Policy sets `AUDIO_OUTPUT_FLAG_INCALL_MUSIC`](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/managerdefault/AudioPolicyManager.cpp#1006) when the selected output is exclusively telephony TX, an explicit device ID was supplied, the format is linear PCM, and either the stream is music or the usage is `USAGE_VOICE_COMMUNICATION`. [Accessible call modes](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/managerdefault/AudioPolicyManager.cpp#6299) include in-call, in-communication, and call-screening. For this cellular gateway, open the tap after Telecom has placed the call in the active/in-call state; the helper need not request the mode itself.

The diagnostic recipe is therefore:

1. With shell UID 2000 and its actual grants/app-op verified, construct context-free `AudioRecord.Builder` using `VOICE_DOWNLINK`, PCM16 mono, and the requested 8 or 16 kHz format.
2. Construct a streaming PCM16 mono `AudioTrack` using ordinary `USAGE_VOICE_COMMUNICATION` and speech content.
3. Enumerate output devices, choose a telephony TX sink, and call `setPreferredDevice()` before playback. The resulting native recreation applies the explicit device and incall-music flag. No hidden output flag needs to be set by the app.
4. Check record initialization and recording state, check observable read/write/routing errors, and verify both directions with known remote signals. Keep the bridge's PCM format agreement and avoid silent sample-rate fallback.

This is physical telephony TX routing. A mode condition accepting `IN_COMMUNICATION` does not turn it into injection into an unrelated VoIP app's capture stream.

## Android 11 permission changes in the supplied patches

Shell's `CAPTURE_AUDIO_OUTPUT` permission was added in Android 11 by the `frameworks/base` commit [`a90b1fcaca8eaac489dc6d90f6feb5abcccf11fc`](https://android.googlesource.com/platform/frameworks/base/+/a90b1fcaca8eaac489dc6d90f6feb5abcccf11fc), **Add CAPTURE_AUDIO_OUTPUT permission required for GTS test**. The helper still needs the complete capture permission/app-op recipe described above.

Both supplied `frameworks/av` patches landed in Android 11. Their permission paths are present in the audited `android-11.0.0_r48` sources, with subsequent implementation changes noted below:

- [`8a1095a9f240b4ac69e8aa47954a3ceb1bd38e16`](https://android.googlesource.com/platform/frameworks/av/+/8a1095a9f240b4ac69e8aa47954a3ceb1bd38e16): **audio policy: fix playback permission checks**.
- [`dbf0a2ee3492723913e898b6aa23e314056c8b86`](https://android.googlesource.com/platform/frameworks/av/+/dbf0a2ee3492723913e898b6aa23e314056c8b86): **Add support for USAGE_VOICE_COMMUNICATION playback capture**.

The permissions belong to the process performing the operation. A dialer role held by the app does not transfer grants to its shell helper. For ordinary clients, the read/write requirements are:

| Operation | Permission requirements on this baseline | Stock shell grant availability |
| --- | --- | --- |
| Read cellular downlink: `AudioRecord` with `VOICE_DOWNLINK` / telephony RX | `RECORD_AUDIO`, an allowed record app-op, and `CAPTURE_AUDIO_OUTPUT`. | Required grants present. |
| Read cellular uplink or both directions: `VOICE_UPLINK` / `VOICE_CALL` | The same recording and output-capture checks. Availability of the requested call channels still depends on the input profile/HAL. | Required grants present. |
| Write PCM into cellular uplink: ordinary `AudioTrack` routed to telephony TX | `MODIFY_PHONE_STATE` for the selected telephony TX output. Ordinary usage does not add `MODIFY_AUDIO_ROUTING` or `CALL_AUDIO_INTERCEPTION`. | Required grant present. |
| Read an app's `USAGE_VOICE_COMMUNICATION` playback through a render/loopback policy mix | `CAPTURE_VOICE_COMMUNICATION_OUTPUT`, plus the policy-registration/capture requirements described below and recording permission/app-op for the `AudioRecord`. | Dedicated voice-communication capture grant absent. |
| Write virtual-source audio into a remote submix feeding local capture | `MODIFY_AUDIO_ROUTING` is the intended output-type check, with authorized mix registration also required. See the Binder-identity caveat below. | Routing grant absent; this is not the supported shell telephony recipe. |

These are permission requirements, not proof of a working route. The patches do not add a writable physical telephony RX endpoint, a generic way to inject into another VoIP app's microphone, or guaranteed HAL support.

### Playback checks: `8a1095a9...`

The patch adds output classification to policy manager/service: legacy output, telephony TX, or virtual-source remote-submix playback. [Manager classification](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/managerdefault/AudioPolicyManager.cpp#1042) identifies output devices consisting exclusively of telephony TX; dynamic virtual-source mixes are classified separately. [Policy service](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/service/AudioPolicyInterfaceImpl.cpp#261) checks `MODIFY_PHONE_STATE` for telephony TX and returns native `PERMISSION_DENIED` on denial. This replaces the previous `INCALL_MUSIC`-flag check and silent retry on the default output. A failed uplink request therefore must not be reported as successful local playback; Java construction/recreation may expose it as a generic initialization failure.

The patch also adds `modifyAudioRoutingAllowed(pid, uid)`, uses it for virtual-source playback, and changes external-policy input capture to check explicit client identity. There is a caveat in this exact patch and the audited release: the [helper's audioserver exemption](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/media/utils/ServiceUtilities.cpp#192) tests the current Binder calling UID, not its supplied client UID. Playback calls it while [Binder identity has been cleared](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/service/AudioPolicyInterfaceImpl.cpp#253), so that remote-submix output check can return true without checking the client's routing permission. This does not grant the caller `MODIFY_AUDIO_ROUTING` or bypass every policy-registration check. The telephony check uses `modifyPhoneStateAllowed(pid, uid)` and is unaffected. Document intended routing requirements separately from this implementation defect; do not use it as a supported integration path.

### Voice-communication playback capture: `dbf0a2ee...`

The patch extends render/loopback mix matching to `USAGE_VOICE_COMMUNICATION`, guarded by the new permission check `captureVoiceCommunicationOutputAllowed(pid, uid)`. This concerns an app's played communication audio, such as VoIP output. Cellular `VOICE_DOWNLINK` capture remains a telephony input using `CAPTURE_AUDIO_OUTPUT`; `CAPTURE_VOICE_COMMUNICATION_OUTPUT` is not required for that direct input path, and `CAPTURE_AUDIO_OUTPUT` does not substitute for the dedicated voice-playback permission.

[`CAPTURE_VOICE_COMMUNICATION_OUTPUT`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/res/AndroidManifest.xml#3972) is signature/privileged, with capture-policy restrictions. Normal microphone approval or MediaProjection consent does not grant it, and the supplied shell manifest/allowlist does not request or supply it. The patch's native permission utility exempts root and audioserver by client UID; it does not exempt shell.

The supplied patch initially detects explicit voice-usage matching rules during mix registration and narrows its media-capture check to privileged mixes matching other usages. The final audited release differs: [AudioService registration validation](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/services/core/java/com/android/server/audio/AudioService.java#8030) checks privileged playback capture, explicit voice-usage matching, and the dedicated permission before setting the voice-capture-allowed flag. Registration also requires `MODIFY_AUDIO_ROUTING`, or a valid audio MediaProjection for the appropriate render/loopback mix. [Native registration](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/service/AudioPolicyInterfaceImpl.cpp#1219) checks the voice flag's permission again. In this snapshot, it additionally checks `CAPTURE_MEDIA_OUTPUT` whenever `mAllowPrivilegedPlaybackCapture` is set, while Java accepts `CAPTURE_MEDIA_OUTPUT` or `CAPTURE_AUDIO_OUTPUT` at its corresponding check. Consequently, do not describe the dedicated voice permission alone, or Java's output-capture alternative alone, as sufficient for the complete privileged policy path.

[Native mix matching](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/common/managerdefinitions/src/AudioPolicyMix.cpp#209) requires the voice-capture-allowed flag for communication usage and still rejects audio that disallows system capture. The dedicated permission therefore does not guarantee that every VoIP application's playback is capturable. It adds capture support, not uplink injection into that application's recording stream.

For the cellular-to-SIP gateway, the supported permission recipe remains `RECORD_AUDIO` + `CAPTURE_AUDIO_OUTPUT` for reading downlink and `MODIFY_PHONE_STATE` for writing telephony uplink. These patches do not require adding the optional VoIP capture/redirection feature to the port.

## Audio construction and attribution

Both builders and [`AudioTrack.Builder.setTransferMode()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioTrack.java#1114) are present, but neither builder has `setContext()`. `AttributionSource` is also absent. Isolate modern classes and context-builder calls; lack of this builder method is a construction difference, not a new permission blocker.

The documented introduction levels are API 31 for [`AudioRecord.Builder.setContext(Context)`](https://developer.android.com/reference/android/media/AudioRecord.Builder#setContext(android.content.Context)) and API 34 for [`AudioTrack.Builder.setContext(Context)`](https://developer.android.com/reference/android/media/AudioTrack.Builder#setContext(android.content.Context)). Thus API 30 has neither setter, API 31–33 has only the record setter, and API 34+ has both. The API 30 absence was rechecked in the supplied `android-11.0.0_r48` source; later introduction levels come from the API documentation. Detect the builders independently at runtime rather than sharing an API 31 guard.

The [Android 12L audit](ANDROID12_SOURCE_AUDIT.md) records the supplied API 32 source separately: explicit record attribution, continued context-free track attribution, and different non-UI Telecom service admission. Keep the Android 11 findings scoped to this tag.

The [record constructor](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioRecord.java#404) supplies an operation-package string to native setup. [Its selection method](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioRecord.java#419) uses `ActivityThread.currentOpPackageName()`, falling back to `uid:<callingUid>` for command-line utilities. [JNI](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/jni/android_media_AudioRecord.cpp#265) initializes the native record with that string and default caller UID/PID. [AppOps package resolution](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/services/core/java/com/android/server/appop/AppOpsService.java#6151) maps UID 2000 to `com.android.shell` and UID 0 to `root` before operation handling.

The [track constructor](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioTrack.java#807) gets its operation package through inherited [`PlayerBase.getCurrentOpPackageName()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/PlayerBase.java#627), which returns the activity-thread operation package or an empty string. Record and track package fallbacks differ; inspect their actual behavior in the helper. The AppOps normalization is encouraging but does not establish every native package check.

Playback has a check before AppOps: [`OpPlayAudioMonitor::createIfNeeded()`](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audioflinger/Tracks.cpp#387) gets the UID's packages and validates a nonempty supplied operation package. With shell's package installed, an empty supplied package selects an associated package, but a nonempty gateway-app package paired with UID 2000 is invalid. The monitor clears an invalid package and [`checkPlayAudioForUsage()`](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audioflinger/Tracks.cpp#467) forces playback denial for that empty monitor package. Recording AppOps normalization therefore does not prove playback attribution works. A track can be created and accept writes while attribution forces it muted.

Use ordinary context-free builders in the production API 30 implementation when natural helper attribution is empty or correctly matches its UID. Inspect Shizuku UserService bootstrap/context initialization to determine that identity. If it supplies a mismatched nonempty app package, use a narrow version-specific construction adapter that actually changes the track's supplied attribution. Any adapter must preserve the real helper UID and use existing grants; `com.android.shell` correctly identifies UID 2000 rather than granting permissions. Validate hidden-API access in the actual process. Reflecting an absent `setContext()` or wrapping only the AudioManager context cannot fix the builders. A separate demo harness is not required for this implementation work.

### Supplied Shizuku UserService bootstrap

UserService bootstrap behavior is controlled by the installed Shizuku server, not the gateway's client API dependency. Downgrading that dependency does not restore older startup behavior. `UserServiceArgs` has no Context-only/attribution option, and switching to a no-argument constructor does not skip Application creation. Inspect effective helper attribution at runtime.

Landed Shizuku commit [284db86](https://github.com/RikkaApps/Shizuku-API/commit/284db86e8cae49030546a5fed7b5bd1a211a5278) introduced the Application bootstrap. Before that change, Shizuku passed a package Context without installing `mInitialApplication`. Assuming no other initialization installs one, Android 11's `currentOpPackageName()` returns null, playback supplies an empty package and AudioFlinger selects a package belonging to the actual UID. Recording supplies `uid:<callingUid>` and shell recording AppOps normalizes to `com.android.shell`. This older path normally needs no operation-package adapter. These are Android 11 findings; newer `AttributionSource` default construction must be checked separately.

In the inspected `UserService.create()`, startup calls `ActivityThread.systemMain()`, loads the gateway package context, creates a default Application with `LoadedApk.makeApplication(true, null)`, installs it as `ActivityThread.mInitialApplication`, and passes it to the service's context constructor. The parsed `--uid` determines the Android user ID; it does not change the process's Linux UID. The actual helper on the target Android 11 device remains untested.

For an ordinary gateway app, [ContextImpl initialization](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/java/android/app/ContextImpl.java#2766) assigns the app package as its operation package; its special case concerns a system-UID package loaded into another UID. [`makeApplication()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/java/android/app/LoadedApk.java#1256) uses an app context, and [`ActivityThread.currentOpPackageName()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/java/android/app/ActivityThread.java#2158) reads the installed application's operation package. The supplied Shizuku path therefore produces a nonempty gateway package for the audio builders while a shell helper still runs as UID 2000. Recording AppOps normalization does not prevent the earlier playback mismatch check from muting that track.

The implemented API 30 adapter preserves the existing application and replaces only its base context with a wrapper overriding the operation package. Android 11 [`ContextWrapper.getOpPackageName()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/java/android/content/ContextWrapper.java#161) delegates to its base; the mutable, hidden `mBase` field at line 63 is the reflective initialization point. `ShellEnv.prepareOperationPackage()` installs this wrapper once before audio construction and verifies `ActivityThread.currentOpPackageName()`: shell uses `com.android.shell`, while root keeps the actual UID and supplies an empty package. When no initial Application exists, it leaves the context-free framework fallbacks intact. Ordinary package metadata, class loading, and the Linux UID are preserved.

Source recheck (2026-10-12): Android 11's [`AudioRecord.Builder.build()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioRecord.java#771) and [`AudioTrack.Builder.build()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioTrack.java#1274) invoke the context-free constructors described above. [`ActivityThread.getApplication()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/java/android/app/ActivityThread.java#2440) returns the same initial Application modified by the adapter, so both constructors read the corrected operation package. The current construction code falls back when each setter is absent and guards `ModernAudioContext` behind API 31, keeping `AttributionSource` off the API 30 path. This verifies the source path addressed by the adapter; hidden-field accessibility in the actual helper and physical audio/HAL behavior on Android 11 remain unverified.

## Routing surface and optional features

Available APIs include [`AudioManager.getDevices()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioManager.java#5575), [`TYPE_TELEPHONY`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioDeviceInfo.java#110) with TX/RX mappings, [`AudioTrack.setPreferredDevice()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioTrack.java#3441), and [`AudioRecord.setPreferredDevice()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioRecord.java#1743). Track preference validates sink direction and forwards the ID to [native `setOutputDevice()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/jni/android_media_AudioTrack.cpp#1222). That surface does not establish native permission acceptance, a compatible profile, HAL routing, or delivery to the remote caller.

Matching native policy confirms the direct-routing recipe and permission set above. Available device profiles, HAL support, helper execution, and microphone-mute effects still need device verification.

Android 11 does introduce [`USAGE_CALL_ASSISTANT`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioAttributes.java#186) and [`Builder.setSystemUsage()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioAttributes.java#800). Their annotations require audio-routing permission, and the call-assistant constant additionally lists phone-state permission. Shell lacks the routing permission. [AudioService validates system usages when registering/updating Java players](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/services/core/java/com/android/server/audio/AudioService.java#6913), and [native policy has separate system-usage validation](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/service/AudioPolicyInterfaceImpl.cpp#51). The dedicated call-interception helpers, redirection flags/modes, and `CALL_AUDIO_INTERCEPTION` are absent, so this constant alone cannot enable the existing modern backend. Use the ordinary voice-communication usage for the candidate backend.

Strategy-wide device routing is a different operation: [AudioService's `setPreferredDeviceForStrategy()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/services/core/java/com/android/server/audio/AudioService.java#1855) enforces `MODIFY_AUDIO_ROUTING`. It is not an interchangeable replacement for per-track preference with this shell configuration. [AudioService `setMode()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/services/core/java/com/android/server/audio/AudioService.java#3814) first checks audio-settings permission, which shell lacks. [`AudioSystem` mode constants](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioSystem.java#164) end at call-screening mode 4, with `NUM_MODES = 5`; the app's current call-redirection mode 5 is absent. Keep existing handset suppression unavailable here unless a separate implementation is verified.

Ordinary public [playback capture](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioPlaybackCaptureConfiguration.java#31) remains limited to media, game, and unknown. Android 11's separate privileged voice-communication exception is described in the [patch findings](#voice-communication-playback-capture-dbf0a2ee); it is not a cellular-downlink fallback and is unavailable to this stock shell configuration.

## Call control and dialer selection

[`RoleManager.ROLE_DIALER`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/java/android/app/role/RoleManager.java#95) and the user-facing role request are present. [Framework `InCallService` documentation](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/telecomm/java/android/telecom/InCallService.java#57) describes a conventional dialer with a dial pad and incoming/ongoing call UI. Matching PermissionController source now confirms that its actual qualifier accepts the planned gateway/recovery-only activity without requiring a normal dial pad. Role qualification and Telecom service binding remain separate checks.

### PermissionController dialer qualification

The supplied `PermissionController` checkout is clean and identifies as `android-11.0.0_r48`. Its [dialer role definition](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/res/xml/roles.xml#166) has exactly two required components: activities handling `ACTION_DIAL` without data and `ACTION_DIAL` with the `tel` scheme. There is no required service or UI metadata in this role declaration.

[`Role.isPackageQualified()`](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/src/com/android/permissioncontroller/role/model/Role.java#551) applies [general eligibility](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/src/com/android/permissioncontroller/role/model/Role.java#647): the installed package must be enabled, must not be the Android system package or an instant app, and must not declare shared libraries. The dialer role is not system-only; [the parser defaults that attribute to false](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/src/com/android/permissioncontroller/role/model/RoleParser.java#362). Ordinary installed apps can therefore qualify.

[`DialerRoleBehavior`](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/src/com/android/permissioncontroller/role/model/DialerRoleBehavior.java#40) supplies no qualification override, and [the inherited default returns null](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/src/com/android/permissioncontroller/role/model/RoleBehavior.java#130). Qualification falls through to finding a component for each XML requirement. [Component matching](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/src/com/android/permissioncontroller/role/model/RequiredComponent.java#104) uses package-scoped PackageManager queries; [`RequiredActivity` adds `MATCH_DEFAULT_ONLY`](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/src/com/android/permissioncontroller/role/model/RequiredActivity.java#43). Add `CATEGORY_DEFAULT` to both manifest filters. One enabled gateway/recovery activity can satisfy both requirements using two filters, one without a data scheme and one with `tel`. No code here launches the activity to inspect its contents or checks functional dial-pad, manual-answer, call-history, or audio features. `CATEGORY_BROWSABLE` is not required by these checks.

This is the normal request path: [RequestRoleActivity checks the package](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/src/com/android/permissioncontroller/role/ui/RequestRoleActivity.java#156), and [RoleControllerServiceImpl checks it again when adding a holder](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/src/com/android/permissioncontroller/role/service/RoleControllerServiceImpl.java#184). `DialerRoleBehavior` makes availability depend on a voice-capable device and visibility depend on `config_showDialerRole`. Qualification does not select the app; retain the explicit user-facing role request.

The manifest recipe is an exported, enabled activity with those two default-category filters, plus a separate enabled/exported `InCallService` protected by `BIND_INCALL_SERVICE`, handling `android.telecom.InCallService`, with `IN_CALL_SERVICE_UI=true` for Telecom binding. Keep the planned gateway/recovery screen rather than adding a normal dial pad for qualification. Keep these components enabled while the app is selected, including when takeover is off or SIP is disconnected. Test actual role selection, both dial-intent forms, and service callbacks after implementing the declarations.

### Permissions granted by the dialer role

The [permission block](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/res/xml/roles.xml#190) expands phone, contacts, SMS, microphone, and camera sets. The microphone set contains `RECORD_AUDIO`. None contains `CAPTURE_AUDIO_OUTPUT`, `MODIFY_PHONE_STATE`, `MODIFY_AUDIO_ROUTING`, `CONTROL_INCALL_EXPERIENCE`, or `CALL_AUDIO_INTERCEPTION`.

[`Role.grant()`](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/src/com/android/permissioncontroller/role/model/Role.java#691) applies configured permissions, app-ops, and preferred activities. [Permissions.grant() intersects the list with the package's requested permissions](https://android.googlesource.com/platform/packages/apps/PermissionController/+/android-11.0.0_r48/src/com/android/permissioncontroller/role/model/Permissions.java#112), subject to permission-state rules. Request only permissions the implementation needs; role selection does not require declaring every listed permission. Grants apply to the app and do not transfer to its shell helper. Privileged call audio continues to use shell's independently established grants.

The role is exclusive, configures preferred activities for both dial-intent forms, and grants `run_any_in_background`. It grants `run_in_background` only through target SDK 25. That condition limits an app-op grant, not dialer eligibility: there is no target-SDK ceiling in the audited dialer qualifier. These app-ops do not establish blanket foreground-service or power-management exemptions.

For an app that has obtained the dialer role, [Telecom service classification](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-11.0.0_r48/src/com/android/server/telecom/InCallController.java#1467) requires `BIND_INCALL_SERVICE` protection, then admits the default-dialer package only when its service declares `IN_CALL_SERVICE_UI=true`. Default-dialer status alone does not qualify a non-UI service in this release. [UI binding](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-11.0.0_r48/src/com/android/server/telecom/InCallController.java#1291) wraps the dialer connection with system UI fallback and selects system handling for emergency calls. A third-party non-UI service instead needs `CONTROL_INCALL_EXPERIENCE`, a privileged permission that ordinary user selection does not grant.

The [default system-dialer runtime grant routine](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/services/core/java/com/android/server/pm/permission/DefaultPermissionGrantPolicy.java#878) covers phone, contacts, SMS, microphone, and camera permissions. It grants no privileged output capture; grants to an app UID do not transfer to the helper. Audio availability on this candidate comes from shell's own new grant configuration.

[`CALL_COMPANION_APP`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/res/AndroidManifest.xml#1197) exists as a normal permission, but `MANAGE_ONGOING_CALLS` and its app-op are absent. The [standalone `telecom` command](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/cmds/telecom/telecom#1) supports [`add-or-remove-call-companion-app <package> <1/0>`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/cmds/telecom/src/com/android/commands/telecom/Telecom.java#309). It calls [a shell/root-only Binder method also requiring `MODIFY_PHONE_STATE`](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-11.0.0_r48/src/com/android/server/telecom/TelecomServiceImpl.java#1802). Shell can change the list. This release provides no Telecom `onShellCommand()` implementation; the current `cmd telecom ...` invocation is not the implementation of this legacy command.

However, changing that list cannot enable the companion binding: [connection setup requests service type `COMPANION`](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-11.0.0_r48/src/com/android/server/telecom/InCallController.java#1344), [component enumeration requires the classifier to return the requested type](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-11.0.0_r48/src/com/android/server/telecom/InCallController.java#1439), and `getInCallServiceType()` never returns `COMPANION` or checks `CALL_COMPANION_APP`. It returns only system UI, dialer UI, car-mode UI, privileged non-UI, or invalid. The [role adapter](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-11.0.0_r48/src/com/android/server/telecom/RoleManagerAdapterImpl.java#98) maintains the test override list, while the real companion-role lookup remains a TODO returning an empty list.

An override appearing in `dumpsys telecom` is therefore a false readiness signal for this tag. Mark ordinary companion integration unavailable and offer explicit default-dialer selection. Validate the selected role and enabled/protected UI-service configuration while idle, then require actual service binding and callbacks during a call before declaring that call controllable. Telecom binds in response to calls; an existing idle binding must not be a prerequisite for placing the first gateway call. Do not keep adding overrides, changing an absent app-op, or presenting the command's existence as functional companion support.

## Optional Xposed call access

This section is deferred research. No Xposed module or app-side hook integration is planned for now. Xposed could change the missing Telecom qualification path and make default-dialer replacement optional on this baseline. There is no companion-permission branch in `getInCallServiceType()` to simply override: a module would need to supply a usable classification path.

| Candidate approach | Required changes |
| --- | --- |
| Admit a non-UI service (preferred) | Hook [service classification](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-11.0.0_r48/src/com/android/server/telecom/InCallController.java#1468) for the exact gateway package/component to return `IN_CALL_SERVICE_TYPE_NON_UI`, bypassing its `CONTROL_INCALL_EXPERIENCE` qualification. Preserve `BIND_INCALL_SERVICE` protection and non-UI/non-car-UI declarations. No companion-list entry is required. |
| Restore companion support | Add a classifier result of `IN_CALL_SERVICE_TYPE_COMPANION` for the intended component, and keep the package in the companion list through the existing override mechanism or a separate list hook. Both classification and list membership are needed. |

The [non-UI binding path](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-11.0.0_r48/src/com/android/server/telecom/InCallController.java#1337) already enumerates these services alongside the selected UI service. [After binding, Telecom supplies an InCallAdapter](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-11.0.0_r48/src/com/android/server/telecom/InCallController.java#1560), whose [answer](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-11.0.0_r48/src/com/android/server/telecom/InCallAdapter.java#52) and [disconnect](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-11.0.0_r48/src/com/android/server/telecom/InCallAdapter.java#275) methods use the normal CallsManager path. This supports the proposed reuse of the gateway's existing call-controller APIs while the user's usual dialer remains selected. Ordinary call-placement permissions, call ownership, and emergency-number rejection still apply.

The hook must execute in the process hosting Telecom, match the actual release/vendor code, and be scoped to the intended gateway component/user. Hooking only the gateway process or globally returning granted permission results is not the proposed implementation. Module installation or an enabled setting does not establish actual hook execution or service binding.

If pursued later, Xposed call access would need its own explicit experimental selection, capability diagnostics, and setup/readiness logic. The non-UI variant would need neither a companion override nor the absent `MANAGE_ONGOING_CALLS` app-op. Validate configuration while idle and binding/callbacks during calls, with no existing idle binding required for the first call. On hook loss, report unavailable call access and refuse new gateway operations; do not silently replace the dialer. Test answer/disconnect, original-dialer operation, manual-call isolation, takeover off, hook loss, Telecom restart/reboot, and cleanup. These requirements are retained for future use, outside the current implementation scope; see the [deferred hook design](ANDROID_COMPATIBILITY_PLAN.md#optional-xposed-call-access-deferred).

A Telecom hook would change call access only. API 30 audio can use the existing shell helper with the audited grants and direct-routing recipe. A future effective audio-permission hook could separately address older capture checks, with a small recording/app-op extension and both PCM directions still in the helper. That conditional design would not require a root audio helper, but it is not part of the current port. Xposed cannot supply missing HAL/modem routes. API 30 remains the provisional stock minimum. No Xposed module or app-side integration was implemented or tested in this audit.

## HAL calls and observable errors

[`AudioTrack::setOutputDevice()`](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/media/libaudioclient/AudioTrack.cpp#1398) stores the requested ID, invalidates/interrupts an existing track, and returns `NO_ERROR`. It does not synchronously establish the HAL route. Output creation can return native permission or configuration failures through [policy](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/service/AudioPolicyInterfaceImpl.cpp#267) and [AudioFlinger](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audioflinger/AudioFlinger.cpp#789). Unlike the earlier Android 10 permission-denial fallback described in its audit, the traced Android 11 policy/AudioSystem/AudioFlinger creation chain propagates telephony TX permission denial; do not generalize the Android 10 fallback here.

Applied output routing follows `AudioPolicyManager::setOutputDevices()` -> `installPatch()` -> policy client/AudioFlinger `createAudioPatch()` -> `PatchPanel` -> playback-thread `createAudioPatch_l()`. The [playback thread](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audioflinger/Threads.cpp#4246) calls `DeviceHalInterface::createAudioPatch()` if patches are supported, or output-stream `setParameters(routing=...)` otherwise. The [HIDL implementation](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/media/libaudiohal/impl/DeviceHalHidl.cpp#320) calls device `createAudioPatch()` or `updateAudioPatch()` and converts transport/HAL results to a native status.

[`installPatch()`](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/managerdefault/AudioPolicyManager.cpp#6531) returns that status and only installs a successful patch. But [ordinary output routing](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/managerdefault/AudioPolicyManager.cpp#5818) ignores its status and returns a mute delay. Unsupported output devices can also retain the previous route. Playback-thread routing state is updated before the HAL call, and a configuration event can be emitted despite failure. Neither a successful setter nor a reported routed device proves remote delivery, and no automatic working-microphone fallback is guaranteed by this path.

Input routing has stronger propagation: [`setInputDevice()`](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/managerdefault/AudioPolicyManager.cpp#5863) returns patch status, and [`startInput()`](https://android.googlesource.com/platform/frameworks/av/+/android-11.0.0_r48/services/audiopolicy/managerdefault/AudioPolicyManager.cpp#2287) uses it and rolls back client activity on failure. At Java level, [`AudioRecord.startRecording()`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/media/java/android/media/AudioRecord.java#1139) throws for an uninitialized object but otherwise only changes recording state if native start succeeds. Check `recordingState`; absence of an exception is insufficient. Track [`JNI start`](https://android.googlesource.com/platform/frameworks/base/+/android-11.0.0_r48/core/jni/android_media_AudioTrack.cpp#531) discards native `start()` status, while Java sets its play state, so `PLAYSTATE_PLAYING` is also insufficient.

Builders can report generic `UnsupportedOperationException` when creation leaves the object uninitialized; constructors can leave `STATE_UNINITIALIZED`. Start/state failures and read/write error codes provide additional evidence, but some routing failures remain observable only through native logs or missing remote audio. Use bounded diagnostics, actual signals in both directions, and full cleanup. The [Telecom mute implementation](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-11.0.0_r48/src/com/android/server/telecom/CallAudioRouteStateMachine.java#1653) requests global microphone mute through AudioService; its effect on injected PCM and handset routes remains a vendor/device test, not a source-proven guarantee.

## Next step and implementation gate

Matching native audio, Telecom, and PermissionController dialer-role audits are complete for this tag. The planned gateway/recovery-only activity satisfies the source-level role requirements when its two default-category dial filters are declared. Next, validate the helper and minimal dialer integration on API 30 and run a real-device diagnostic. Remaining checks:

1. Actual shell grants, record app-op, context-free construction/operation-package handling, hidden-API access, and bounded start/I/O behavior in the helper.
2. Device telephony RX/TX endpoints and compatible profiles, native-library loading, and remote two-way PCM delivery during a live cellular call, at 8 and 16 kHz independently.
3. HAL failure symptoms, microphone mute, handset output, and return to normal routing; reported preference and frame counters cannot prove delivery.
4. Actual user role selection, both dial-intent forms, idle role/component validation, UI-service binding and callbacks during calls, and gateway/recovery behavior. Source-level role qualification is established. Companion mode remains unavailable on the audited baseline; verify any vendor-specific alternative separately.

API 30 is the recommended provisional stock unrooted minimum with default-dialer call control. Implement the path directly in the existing app and use its calls for subsequent helper/device verification; a separate demo phase is not required. Raise the target only if an essential compatibility requirement blocks it; vendor-specific HAL failures should be recorded as device limitations. Keep optional audio/call-control settings and modern feature isolation from the existing plan, while clearly stating that refusing dialer selection on the unmodified baseline leaves gateway call access unavailable. Xposed integration and API 23–29 support are deferred. No runtime implementation or device audio test was performed in this audit.
