# Android 13 call access and audio redirection audit

Audited `android13/{base,av,Telecomm}`, all at `android-13.0.0_r84` (API 33). Coverage includes relevant Telecom admission/tests, Java audio construction and attribution, shell permission declarations, and native policy permission/routing checks. Initial Android 13, PermissionController qualification, vendor HALs, and physical-device binding/audio were not separately verified. See the [Android 12L audit](ANDROID12_SOURCE_AUDIT.md) for the preceding baseline.

## Non-UI call admission continues

[`InCallController`](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-13.0.0_r84/src/com/android/server/telecom/InCallController.java#1843) retains the non-UI classification for a service declaring neither UI nor car-mode UI and having either `CONTROL_INCALL_EXPERIENCE` or permitted `MANAGE_ONGOING_CALLS`. The [permission check](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-13.0.0_r84/src/com/android/server/telecom/InCallController.java#2341) uses attribution-aware PermissionChecker data delivery. This branch does not require a test companion-list override or default-dialer role.

[`testBindToService_ThirdPartyApp()`](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-13.0.0_r84/tests/src/com/android/server/telecom/tests/InCallControllerTests.java#1024) retains the verification that Telecom binds the system dialer and the permitted third-party non-UI service. This upstream unit test was inspected, not run; it tests admission, not audio injection.

The app's readiness check uses the non-UI admission requirements on API 31+: enabled non-UI service, allowed AppOp, and calling permissions. API 30 retains the default-dialer requirement. The former API 34+ override requirement was an app restriction with no established framework basis and has been removed after checking the current Android 17 implementation below.

### Current framework follow-up: Android 17

The supplied root `Telecomm` checkout is `android-17.0.0_r1` (API 37). Its [`getInCallServiceType()` branch](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-17.0.0_r1/src/com/android/server/telecom/InCallController.java#2799) still admits our non-UI service through permitted `MANAGE_ONGOING_CALLS`. [`updateNonUiInCallServices()`](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-17.0.0_r1/src/com/android/server/telecom/InCallController.java#2444) adds the non-UI services independently, then performs a separate companion-list lookup requesting `IN_CALL_SERVICE_TYPE_COMPANION`. [`RoleManagerAdapterImpl.getCallCompanionApps()`](https://android.googlesource.com/platform/packages/services/Telecomm/+/android-17.0.0_r1/src/com/android/server/telecom/RoleManagerAdapterImpl.java#124) returns the override list for that second lookup. The list is not a requirement for NON_UI admission. The inspected classifier has no branch returning COMPANION; adding an override alone does not change the service's classification.

This follow-up covers current Telecom admission only, not an Android 17 audio audit or separate Android 14–16 tag audits. Readiness no longer invents an override requirement for those versions; actual AppOp/component checks and call callbacks remain necessary. The regression checks readiness across API 31–37 with the override absent.

## Builder and default attribution paths

[`AudioRecord.Builder.setContext()`](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r84/media/java/android/media/AudioRecord.java#632) exists, and the [constructor](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r84/media/java/android/media/AudioRecord.java#449) uses its explicit context attribution when supplied. `AudioTrack.Builder.setContext()` is absent; the [track constructor](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r84/media/java/android/media/AudioTrack.java#822) still supplies `getCurrentOpPackageName()` to native setup. Independent setter detection remains necessary.

[`AttributionSource.myAttributionSource()`](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r84/core/java/android/content/AttributionSource.java#212) now prefers `ActivityThread.currentAttributionSource()`. Without an Application source it obtains a package for the process UID, mapping root to system UID in this fallback, and throws `IllegalStateException` if resolution fails. This differs from the audited API 32 implementation, which constructs its default source from the process UID and current operation package.

The existing modern adapter covers the Application path by overriding both `getOpPackageName()` and `getAttributionSource()` while preserving the Application and its ordinary package metadata. The first override addresses track construction; the second addresses default record/helper construction on API 33. It verifies the resulting identity. Root bootstrap without an Application can fail the actual-UID verification because the framework fallback substitutes system UID; the app must report this failure rather than silently claim valid root attribution. This root variant was not tested on a device.

## Redirection APIs and permissions are present

[`CALL_AUDIO_INTERCEPTION`](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r84/core/res/AndroidManifest.xml#5076) is `signature|privileged` on this tag, and the [shell manifest](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r84/packages/Shell/AndroidManifest.xml#632) requests it alongside the existing recording, output-capture, phone-state, and audio-settings permissions. Selecting the default dialer does not establish this privileged audio grant; inspect the actual helper grants.

The hidden/SystemApi helpers [`getCallUplinkInjectionAudioTrack()`](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r84/media/java/android/media/AudioManager.java#8170) and [`getCallDownlinkExtractionAudioRecord()`](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r84/media/java/android/media/AudioManager.java#8242) are present. Both use context-free builders. The uplink helper specifies system usage `USAGE_CALL_ASSISTANT`, speech content, and the current call-redirection mode; the downlink helper specifies `VOICE_DOWNLINK` and that mode. Both register a [mode listener](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r84/media/java/android/media/AudioManager.java#8289) that releases clients when the corresponding PSTN/VoIP mode becomes incompatible.

[Format/mode selection](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r84/media/java/android/media/AudioManager.java#8103) accepts PCM16 or float, 8–48 kHz, and mono/stereo. PSTN modes include IN_CALL, CALL_SCREENING, and CALL_REDIRECT; communication modes select VoIP redirection. The cellular gateway must still check call ownership and PSTN mode before using these helpers.

[`isPstnCallAudioInterceptable()`](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r84/services/core/java/com/android/server/audio/AudioService.java#5744) enforces interception permission and checks that telephony TX and RX devices are enumerated. It does not exercise a HAL route or verify remote audio. Helpers can report `NullPointerException` for a null format, `UnsupportedOperationException` for unsupported format/device accessibility/construction/listener registration, `IllegalStateException` for an incompatible mode, and permission failures. Reflection may wrap these failures in `InvocationTargetException`.

[Native telephony TX admission](https://android.googlesource.com/platform/frameworks/av/+/android-13.0.0_r84/services/audiopolicy/service/AudioPolicyInterfaceImpl.cpp#392) requires interception permission when the call-redirection flag is present and also checks `MODIFY_PHONE_STATE`. [Call-source recording](https://android.googlesource.com/platform/frameworks/av/+/android-13.0.0_r84/services/audiopolicy/service/AudioPolicyInterfaceImpl.cpp#617) checks recording access and permits call capture with either interception or output-capture access; other redirection checks still apply. [`AudioService.setMode()`](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r84/services/core/java/com/android/server/audio/AudioService.java#5547) requires phone-state permission for call/communication redirection modes.

## Direct routing remains available

The [ordinary telephony TX selection](https://android.googlesource.com/platform/frameworks/av/+/android-13.0.0_r84/services/audiopolicy/managerdefault/AudioPolicyManager.cpp#1240) still selects `INCALL_MUSIC` for explicitly preferred telephony TX, linear PCM, voice-communication usage (or music stream), and accessible call audio. Ordinary playback without the redirection flag retains the phone-state check. Direct downlink can retain the recording/output-capture recipe. The app's existing direct and redirection backends therefore remain separate choices on this tag. Actual HAL support, handset suppression, and two-way audio still require device verification.

Validation (2026-10-12): `:privileged:testDebugUnitTest` passed all 23 app-side tests, including the readiness regression extended to API 33. Source citation targets and whitespace were checked. Upstream Telecom/CTS tests and physical-device binding/audio were not run.
